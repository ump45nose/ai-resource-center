# 重构必须保留的现有数据

2026-10-22 已从旧中心一致快照完成首次交接。新版数据位于 fn 的 `/vol2/1000/Docker/ai-resource-center-v2/data`；旧服务及 `/vol2/1000/Docker/ai-resource-center/data` 继续保留。新版保存的人工修改以新版为准，旧版后续写入尚不自动镜像。

## 站点、账号和渠道是三层对象

站点保存网站、签到入口和别名；账号保存余额、签到及权益；渠道保存调用地址、模型、协议、用途、凭据引用和应用绑定。共享账号余额不能按模型或渠道重复计算。

保留现有稳定 ID、`siteId`、`accountId`、来源标识和 `refs` 关联。网址用于展示和辅助匹配，不代替来源 ID。不同入口、签到域名和已确认别名也要保留。

旧库用途值为 `general/media/rp/client`。新版用 `usage=general/image/video`，分别对应通用、生图、视频；渠道只放一个管理分组。能力、限制标签和实际应用记录仍独立保存。旧 RP 记录保留 `usage=rp` 与 `category=rp` 作为来源，但已移出中心（见下文）。

迁移时保留原值作为来源：旧 client 按已有明确要求生成“客户端限定”；生图／视频根据原模型与记录保留能力。只有明确规则才添加“禁止 NSFW”或“仅能用于代码”。已有人工限制、备注和例外优先保留，不因合并或来源更新丢失。

共享地址、协议、凭据和标签归渠道。不同原生连接可以关联同一渠道，不以合并站点为由合并独立 key。

## RP 渠道移出中心

2026-11-06 起 RP 渠道只在酒馆和 Chrome 书签中管理。服务启动时 `migrateRpRemoval` 处理一次：发现未移除的 RP 渠道（`usage=rp`，或旧记录的 `category=rp`、原生凭据引用）就执行，执行后写入设置 `migration:rp-out-of-center-v1`，之后不再重复；没有 RP 渠道时不写记录，也不做任何修改。

- 渠道沿用永久移除的语义：`enabled=false`、`availability=已移除`、`management.state=removed`、`recoveryPolicy.enabled=false`，并写入 `removal={kind:"rp",reason,at}`。版本加一，`actions` 留下记录。
- 站点只有 RP 渠道且没有 All API Hub 关联账号（含委托给插件签到账号的账号）时，设为 `removed=true` 并写同样的 `removal`；其他站点保留。账号从不修改。之后任何来源（含手工新建同址站点）重新提供该站点时自动恢复，并记一条 `restored` 动作。
- 记录、凭据、事件、调用、评估、扫描和旧酒馆绑定全部保留；未完成的 `sillytavern` 同步任务标为 `superseded` 并写明原因。
- 设置中的 `removed.channels`／`removed.sites` 按 ID 保存被改字段的原值；`bookmarks` 保存每个 RP 渠道当时对书签计划的贡献（站点、地址、归档原因）及站点当时的标题、网址和识别地址，书签计划据此保持“酒馆”目录与 RP 归档条目不变。
- 撤销：停止服务后执行 `node scripts/revert-rp-removal.mjs 数据目录`（预览）或加 `--apply`，按原值恢复渠道与站点，把记录移到 `migration:rp-out-of-center-v1:reverted:<时间>`，然后部署仍管理 RP 的旧版本；继续运行本版本会在下次启动时再次移出。

## All API Hub 账号字段归属

账号名称（`site_name`）、站点地址、签到入口（`customCheckIn.url`）和账号启停归插件。中心的站点名称、`checkinUrl`、账号 `enabled` 与 `checkinEnabled` 只在中心、Notion 和书签中使用，不回写插件。中心只决定自动签到开关：签到归档或委托独立签到账号时停止，解除后恢复。

同步记录（`targetLink`，`all-api-hub:<账号 ID>`）新增：`reported={at,snapshot}` 为最近一次插件回执的快照；`checkinHold={reason,at}` 表示中心的停止尚待恢复；`decidedRevision` 为已经处理过的决定摘要，同一决定不再重复下发。任务记录的 `payload` 只含账号标识与决定（`automaticExecutionEnabled`、`reason`），领取时实际回显给插件的名称、签到入口和停用状态存于 `echo`。升级时 `migration:hub-checkin-writeback-v1` 把旧版遗留的冲突与未完成任务按插件当前值清除，并记录清除前的冲突快照。

## 哪些内容不能被同步覆盖

- 人工启停、限制标签、应用绑定、排序、备注、评价、权益规则与归档决定。
- 人工选定的模型、协议、请求头、客户端要求和应用绑定。
- 网关当前配置、中心期望配置、应用回执及冲突记录：保存与生效分别记录。
- 账号来源观察的状态与人工渠道启停：两者不是一个开关。

余额保留数值、单位、来源及观察时间；权益保留有效期、重置时区、签到门槛、投放时刻和已确认的开放窗口。未知值继续保留未知，不推算签到奖励或开放结束时间。

## 问题状态分别保留

网站是否可访问在站点上；API 调用错误、发生时间和所用模型在渠道或调用记录上；无法签到在账号权益中。`apply` 的“待应用”不是上游调用错误。

旧版 `channel.availability` 还承载以下人工清单状态，迁移时按含义接收，不在导入时从一次成功调用反推恢复。迁移后，维护／关闭资源按新版[自动维护规则](requirements.md)验证并恢复；明确移除或禁止使用的决定继续保留：

| 旧值 | 含义 |
| --- | --- |
| `归档-无余额无签到` | 额度耗尽且无法补充 |
| `归档-网站或key失效` | 网站或 key 失效 |
| `归档-调用不稳定` | 人工判定不稳定 |
| `待复核-调用失败` | 调用失败，等待处理 |
| `暂停维护(模型不足或者服务维护)` | 维护或无可选模型 |
| `已移除` | 当前清单不展示，历史记录仍保留 |

限流、余额不足、账号验证和 key 问题影响当前可用性，不直接等于模型质量差。维护、网站打不开与失效不互换。

## 失败渠道也是首次接入的必迁数据

从旧中心最新库迁入全部现存失败渠道，不限于 New API／插件当前仍列出的条目：网站打不开、调用失败、不稳定、维护／模型不足、限流、额度耗尽、key 缺失／失效等都保留。扫描记录中的模型、错误、发生时间、凭据引用、人工处理和历史附件跟随原 ID 迁移；旧表格和报告只补缺失记录，不覆盖之后的更新。

历史失败不会直接算成当前失败率样本。渠道保留最近问题与证据时间，在“归档”的对应问题类型中显示复查计划或等待条件。维护、关闭、不稳定可以参与后续验证恢复；无额度、无 key、未注册分别等待对应条件；“禁止测活”仅被动更新；明确移除／禁止使用不自动恢复。不能把所有旧“归档”都解释成永久删除，也不能导入后全部立即测试。

## 事实记录和附件一起迁移

- 签到按来源与事件 ID 去重；业务日期、时区、执行方式、结果及已确认奖励均保留。
- 调用记录按 `(source, source_id)` 唯一；保留渠道、模型、时间、结果、错误分类、耗时、首字、流式终态和上游请求标识。
- `origin` 保留原调用来源，`legacy_import` 标记首次迁入的历史样本；源端重新确认的真实记录清除此标记。`token_basis` 区分上游 Token 与本地估算。缺终态、缺采集和待关联记录不能改成成功，也不能混入完整成功率。
- 评估保留渠道、模型、客户端、执行区间、结果、人工评价及 Pi、生图、视频等实测记录。少量任务成功不等于长期稳定。
- `evaluation-images` 与评估中的 `image.file` 配套保留；扫描、审计与人工变更附件也在数据卷中。

“禁止测活”渠道只接收真实使用、来源资料和人工更新。导入、编辑、排序、保存和迁移本身都不发起上游请求。

## 旧数据库和凭据的读取入口

SQLite 表为 `entities`、`refs`、`credentials`、`events`、`calls`、`actions`、`auth`、`settings`；`entities` 包含站点、账号、渠道、评估、调用身份和模型扫描对象。完整字段定义见旧工作区的 `server/store.mjs`，业务 JSON 字段见对应模块。

`credentials` 使用 AES-256-GCM 加密，必须与原 `master.key` 配套。沿用旧 `Store.reveal` 读取引用的凭据；不将明文 key 写进迁移日志、前端或 Git。管理登录和扩展权限也随快照保留。

All API Hub 继续使用现有上报入口。接替旧版时需要承接它们的事件去重和授权范围。旧酒馆上报入口已退役，返回 `410`。
