# 公益资源管理：需求与开发阶段

2026-10-21 需求方案，已纳入独立 WebUI 的最新决定。服务端已有基础实现，WebUI 当前为独立预览骨架；本轮按[来源接入与数据同步](source-sync.md)接入 All API Hub 和 New API。CPA 第一版不接入。2026-11-06 起 RP 渠道整体移出中心，只在酒馆和 Chrome 书签中管理（见[RP 渠道不在中心管理](#rp-渠道不在中心管理)）。

## 要解决的问题

作为公益站的使用者，不再靠表格、浏览器插件和多个后台拼凑信息：在独立 WebUI 集中管理资源，在 Personal Data Hub 随手查看和处理；系统持续发现、验证、恢复可用渠道，让现有客户端和任务继续使用。

本项目负责独立 WebUI、fn 上的业务服务、标准 HTTP API 与 MCP。Hub 的布局和界面由 Hub agent 负责；本项目为其提供接入能力和对接方案。

## 产品形态：完整管理入口与标准能力并行

- **独立 WebUI**：完整管理入口，可直接通过浏览器使用，不依赖 Hub 开发进度。桌面适合整理、比较和配置；手机至少能查看、补资料、处理提醒及追踪操作结果。
- **Personal Data Hub**：日常聚合入口，可以使用摘要、提醒、查询和管理 API，也可以跳转 WebUI 的对应站点。展示多少、怎样布局由 Hub agent 决定。
- **HTTP API／MCP**：对外提供相同的业务动作，分别供应用集成和 Agent 调用。WebUI 也使用标准 API，不增加只有页面能做的隐藏操作。

三种入口共用对象、状态、版本与操作记录。例如在 WebUI 补 key，Hub 下次读取就能看到新状态，Agent 可以查询后续验证进度，无需再同步三份资料。Hub 不在线不影响 WebUI，浏览器关掉不影响 fn 的自动维护，管理服务停机不影响已配置的推理调用。

fn 保存资源关系、凭据及维护规则，执行来源同步和维护工作；已有 cron 负责其任务执行，New API／CPA 负责推理转发。建议 WebUI 与资源 API 同源提供，复用服务的登录和权限，不引入第二套管理后台。具体运行框架和部署拆分在详细设计时确定。

## 从日常使用安排能力

| 使用情境 | 用户能完成什么 | 服务应提供什么 |
| --- | --- | --- |
| 随手查看手上的资源 | 看余额、签到、可用模型和近期变化 | 按站点聚合的资料、今日摘要、来源与更新时间 |
| 想用某个模型 | 找到提供该模型的站点，判断是否值得用 | 模型跨站查询，自己的验证结果、站方指标、权益及接入状态 |
| 站点维护或关闭 | 不必一直手工重试 | 周期复查、任务验证、自动恢复、维护记录 |
| key 失效或站点搬家 | 在一个入口补资料，保留历史 | key 更新、入口与别名维护、受影响连接和同步结果 |
| 额度当天过期或限时投放 | 优先利用，不误改任务计划 | 权益规则、New API 同模型渠道优先级、现有 cron 任务绑定 |
| 新模型出现 | 定期测试后纳入资源清单 | 新模型发现、任务评估、归类和 New API 更新 |

衡量结果：日常查看不再依赖旧表格；补 key 不必重复改多个后台；允许主动检查的渠道恢复不必逐个确认；已知维护问题不反复占据待办。

## 哪些能力归谁

| 组件 | 职责 |
| --- | --- |

| 公益资源服务 | 站点与来源关联、人工规则、模型验证、维护状态、权益、配置同步和处理事项的业务记录；HTTP 与 MCP 共用业务逻辑 |
| Personal Data Hub | 按自身需要接入摘要、查询、操作和提醒；通过现有 hub-api 接入，布局由 Hub agent 决定 |
| All API Hub | 浏览器登录、签到执行、账号余额观察与新增账号发现；结果交给资源服务。账号名称、地址和签到入口以插件为准；中心只回写“停止或恢复自动签到”，用于签到归档和独立签到账号 |
| New API | 普通渠道聚合和实际转发；接收通过验证的渠道、模型及路由优先级 |
| CPA | 当前只有订阅反代，保持原运行方式；第一版不接入资源同步和公益渠道流程 |
| CC Switch／Magpie | 使用 New API 聚合配置；仅无法经 New API 中转的客户端限定资源需要专用配置 |
| fn cron 调度层 | 保留任务定义、调度和投递；执行所选任务并回传结果 |
| SillyTavern 与 Chrome 书签 | RP 连接的唯一管理处；中心不接收、不下发酒馆配置或调用 |
| Token Monitor | 用量采集与统计；服务建立渠道关联，不复制费用账本 |
| image-caption | 生图／视频任务验证的前置依赖，完成后再联调接入 |

资源服务保存跨来源关系与自身业务记录；余额、签到和调用事实保留来源与观察时间。Hub 继续作为聚合与操作入口，不把业务规则复制到客户端。资源服务不进入推理转发链路，停机不影响已配置的调用。

## WebUI 围绕查资源、选渠道和处理问题

默认打开站点视图。顶部只放当日权益、签到和需要人工处理的简短摘要，不另做一页以数量和图表为主的大屏。主要导航为“站点、模型、接入与同步、扫描与测试”；全局策略与授权放在设置。核心交互是来源接入、持续同步与渠道扫描测试，补 key 和合并只是辅助操作。

| 入口 | 用户需要看到什么 | 就近完成的操作 |
| --- | --- | --- |
| 站点 | 每站一行，网站及签到链接、账号余额与有效期、签到结果、可用模型摘要、状态和更新时间 | 搜索、用途筛选、置顶、编辑、补 key、暂停、批量整理；维护和关闭站点通过筛选查看 |
| 站点详情 | 账号与共享额度、调用连接、模型验证、签到规则、投放时间、绑定任务及历史 | 修改入口、权益和备注；查看同步结果；没有“禁止测活”标签的连接可按策略发起检查 |
| 模型 | 同一模型在哪些站点可用，站方指标、自己的验证与真实任务表现分别列出 | 按强模型／执行模型、用途和可用性筛选；比较渠道并打开站点；不替调用方选模型 |
| 接入与同步 | 各来源的授权状态、同步范围、最近更新时间、数据变化与失败原因 | 接入检查、首次同步预览、立即同步、查看新增和待关联资料 |
| 扫描与测试 | 扫描候选、逐渠道模型进度、实际任务结果、最近恢复和 New API 生效情况 | 选择范围、批量扫描、安排任务验证、查询等待和失败原因；按“禁止测活”标签排除主动请求 |
| 设置 | 自动维护策略、提醒偏好、现有 cron 任务与绑定 | 调整策略、选择任务和时间条件；任务正文及调度实现仍归原系统 |

通用、生图、视频是三个互斥用途入口；是否允许测试另外由渠道标签决定。带“禁止测活”标签的渠道不提供测试动作。签到入口挂在站点行，签到历史与权益在对应账号下查看。

### 关键操作应当一次完成

- **查模型**：搜索模型 → 比较提供它的渠道和实际表现 → 查看已接入 New API 的情况及使用限制。
- **来源接入**：配置来源及授权 → 检查能力 → 预览同步范围 → 启用同步 → 查看首次同步的数据变化。
- **持续同步**：查看各来源更新情况 → 同步单个来源 → 查看新增、更新和未完成项；连接成功与数据同步完成分别展示。
- **扫描与测试**：选择渠道范围 → 扫描目录与站方指标 → 查看候选 → 安排任务验证 → 查看实际模型结果和网关生效状态。
- **自动恢复**：维护中看到等待或运行原因 → 验证通过 → 显示恢复的具体模型和网关回读结果；无需逐条确认恢复。
- **绑定限时任务**：在站点权益或设置中选择已有 cron → 保存资源条件和明确的时间调整 → 查看实际运行结果。

站点 URL 必须直接可点击；内部 ID 不充当主要名称。主提示使用“等待 19:00 投放”“需要补 key”等具体原因，HTTP 错误放在详情。空白数据写明未取得，过期观察显示最后更新时间。普通编辑不弹重复确认，批量合并等影响多个对象的操作先预览。

## 一份资源数据，两种查找方式

站点、账号和渠道分开：同站多个来源聚合展示，同站不同账号保留独立余额。网站、签到地址、API 地址可不同；已确认的迁移入口和别名关联到原站点。

- **按站点找**：直接提供可点击网站和签到链接，展开账号、余额、渠道、模型、规则及历史。
- **按模型找**：列出提供该模型的站点及渠道，比较实际可用性、任务表现与资源限制。
- **按问题找**：网站打不开、调用失败、key 缺失或失效、余额耗尽、限流、维护分别筛选。无法签到单独标注，不作为调用错误。

### 三个用途入口，限制放在状态列

WebUI 以通用、生图、视频三个互斥用途分组管理渠道，默认通用。能力与限制仍独立保存，不用限制标签代替用途入口。强模型／执行模型仍是模型能力分类。

| 渠道标签 | 约束 |
| --- | --- |
| 客户端限定 | 记录允许的客户端、协议、认证和请求头；只用符合要求的调用方式验证与分发 |
| 禁止测活 | 不发起网站探查、模型目录／广场扫描或测试任务；只接收来源资料、真实调用和人工更新 |
| 禁止代码 | 不安排编程任务，也不推荐或绑定给 Code 用途；允许符合其他限制的聊天 |
| 禁止 NSFW | 不推荐或绑定给 NSFW 用途 |
| 仅能用于代码 | 只推荐或绑定给 Code 用途；允许符合限制的代码验证任务 |

标签可以组合，“禁止代码”和“仅能用于代码”不能同时设置。渠道可具备多种能力，但日常管理只放在一个用途分组。分组调整不自动添加限制标签。客户端限定不等于仅能用于代码，Claude Code 测试通过也不等于客户端限定。

标签约束中心安排的任务与配置分发，并随连接元数据提供给使用端；中心不检查实际对话内容。网站别名和相同凭据的重复记录不能绕过“禁止测活”；同站不同凭据的独立渠道不一刀切禁测。

旧 Code／client 记录仅在已有明确客户端要求时迁移“客户端限定”，不推断“仅能用于代码”。已确认的其他站规迁移为对应标签。来源同步保留人工标签。

### RP 渠道不在中心管理

2026-11-06 决定：RP（酒馆）渠道整体移出中心，只在酒馆和 Chrome 书签中管理。中心与酒馆之间的双向协议从未接通，酒馆侧没有实现，因此一并移除。

- 新增、修改和批量整理都不能把渠道放进 RP 用途；已移出的 RP 渠道不能被重新启用。
- 现有 RP 渠道由一次性迁移软移除并写明原因，记录和历史调用全部保留。迁移后它们不出现在站点、概览、模型、待处理事项、签到、MCP、New API 和 Notion 中。
- 站点还有其他渠道，或有 All API Hub 关联账号（含独立签到账号代签）时保留，余额与签到照常；只有 RP 渠道且没有插件账号的站点同样软移除，之后若来源重新提供该站点会自动恢复。
- Chrome 书签的“酒馆”目录和 RP 相关归档条目保持迁移时插件已镜像的内容，中心不再改动它们；RP-only 站点也不会因为只剩账号而落入“通用”。

自动合并以来源标识、已确认别名和既有关联为依据。相似名称或同一域名下多个账号只生成合并建议，不合并余额。人工合并显示受影响账号与连接，保留原来源和历史引用。

## 自动维护恢复的是渠道和模型

主流程：检查网站与 API → 读取 key 的模型目录 → 复用已有扫描工具筛选模型 → 任务验证 → 更新 New API 并回读 → 记录恢复结果。

网站失败不阻断 API 检查；能读取模型目录也不等于模型调用成功。站方成功率、自己的目录和真实任务结果分别保存。

| 对象或问题 | 处理方式 |
| --- | --- |
| 正常渠道 | 持续接收真实调用；定期更新模型目录，避免无必要的重复任务 |
| 维护中渠道 | 定期扫描模型与 key 状态；有可用候选时验证，通过后自动恢复对应模型 |
| 关闭站点 | 低频检查网页 HTTP 可达性及 API；发现可用 key、可调用模型或可确认的剩余额度时通知；任务通过后自动恢复 |
| 限流、资源投放时刻未到 | 记录原因并按规则安排下一次检查，不算长期质量差 |
| 余额耗尽 | 看是否可签到补充或会重置；不能补充的保留归档原因，不持续消耗式重试 |
| key 缺失或确认失效 | 汇总提醒补充；不重复对已知无效凭据跑任务 |
| 明确移除或禁止使用 | 保留历史，不因来源再次出现就自动恢复 |
| 禁止测活 | 跳过主动检查与任务验证；通过真实调用、来源观察或人工更新维护状态 |

历史扫描失败、维护、关闭和不稳定渠道必须一起接入，不以当前 New API 启用清单作为完整资源库。它们仍是原渠道，在“待恢复”视图查看，保留具体错误、模型、时间、凭据引用及下一次检查安排；不另建一份失败渠道表。明确移除的记录保留历史但不参加恢复。

维护周期、任务验证频率、每轮候选数量和消耗上限是可配置策略。实施时依据站点窗口与选定任务设置，不把旧版评分阈值直接当成新产品结论。

验证任务遵守渠道标签：禁止代码的用非编程任务，仅代码的用代码任务，客户端限定的用相应客户端或已验证的 New API 中转；生图／视频仍等待 image-caption。

恢复粒度是“渠道＋模型＋已验证调用方式”：一个模型通过，不连带恢复同站全部模型。中途切换备用渠道的任务只给实际执行渠道记结果。

自动恢复更新 New API，不自动切换客户端当前配置。客户端限定资源先验证经 New API 中转是否可用；通过则统一纳管，否则保留对应客户端的协议、认证与请求头配置。

## 模型分类用于筛选，不接管选模

| 分类 | 用户给出的初始方向 | 主要观察 |
| --- | --- | --- |
| 强模型 | GPT、Claude、Kimi 等适合思考架构的模型 | 复杂任务完成情况、方案与推理质量 |
| 执行模型 | DeepSeek F、GLM F 等快速执行模型 | 指令执行正确性、速度和稳定性 |

定期发现新型号与版本，按适合的任务评估后接入；品牌不永久决定档次。任务完成和内容质量分别记录：只有 HTTP 成功或进程退出成功，不能直接判为优质。优先使用任务已有的验收结果，必要时保留人工评价。

调用方自己选择模型。本服务不增加“强模型／执行模型”的虚拟调用入口，不负责跨模型智能选路。New API 的优先级调整只在请求模型与能力匹配的渠道间生效。

## 权益和 cron 让现有资源真正被用上

保留当日有效额度、长期额度、签到余额门槛、重置时区、有效期、投放时刻及明确开放窗口。投放时刻不推算成一整段可用时间。不同单位的额度不直接相加。

在可用性和任务要求满足的条件下，New API 优先消耗当日额度；额度过期或耗尽后退出优先池。当前不可用原因与长期质量分别计算。

WebUI 提供任务绑定配置；Hub 和 Agent 可以通过相同接口列出 fn 现有任务，选择要绑定的任务、渠道／模型和可用时段。资源服务把绑定交给现有执行链路，不重建 cron。保留任务 ID、原计划、暂停状态和投递位置；需要调整运行时间的绑定必须显式保存该调整。资源不可用时遵守该任务自己的跳过或备用规则，不替调用方选模型。

接入后优先用选定的真实 cron 任务验证。没有合适任务时，文字渠道可使用明确配置的小任务；具体任务和消耗限制在启用自动维护时设置。生图／视频自动验证等待 image-caption，当前先管理资料与历史结果。

## 少打扰、少填写的便利能力

- 新增站点自动带入来源已有资料，只列出待补 key、用途或规则。
- 搜索同时覆盖站点、网址、别名和模型；可按用途、能力、可用性和权益筛选。
- 站点搬家沿用历史，展示受影响连接；向新域名使用原凭据须有已确认关系。
- 支持置顶、批量归类、暂停和合并预览；不让用户逐页找同一站点。
- 处理事项附带原因、可执行动作和目标站点：补 key、登录、确认关联等。
- 自动恢复和新模型接入汇总为变化记录；同一未解决问题不重复提醒，解决后移出待办。
- 已知维护、已归档、数据源离线不是一组红色调用错误。信息过期时展示最后观察时间。
- 可查看“为何被恢复／降级”“配置已保存还是已生效”，而不是猜测后台做了什么。

## 分阶段交付，每阶段都能使用

| 阶段 | 实现范围 | 交付与完成条件 |
| --- | --- | --- |
| 资源管理可用 | 全量历史资源及失败记录迁移、渠道标签、来源关联去重、余额签到、站点与模型查询、人工维护；独立 WebUI 与基础 HTTP／MCP 同步交付 | 不依赖 Hub，即可在 WebUI 完成查看、补资料和整理；桌面及手机关键操作可用；现有记录及人工决定完整保留；Hub agent 获得对接契约 |
| 文字资源自动维护 | 扫描、新模型评估、cron 接入、恢复与提降权、New API 回读、当日额度和限时绑定；WebUI 提供策略配置及维护进度 | 一条维护渠道能经历发现、验证、自动恢复、调用记录回流；失效 key 不误报模型差；任务不重复执行；页面和 MCP 能查询同一次维护结果 |
| 使用端联动 | 必要的客户端专用配置分发与实际应用回执；WebUI 提供同步状态与冲突处理 | 客户端配置生成与生效有明确区别 |

Hub 可按第一阶段契约并行，不必等待整个后端完成；独立 WebUI 的交付也不等待 Hub 布局。生图／视频验证在 image-caption 就绪后独立接入，不阻塞文字资源阶段。

各阶段最后做对应的迁移、接口、真实链路验证。首次全量交接已完成；承接旧插件上报时只同步各来源负责的字段及事件，不用旧快照覆盖新版人工更新。

### 用这些实际结果验收

- WebUI 能独立完成日常管理；Hub／MCP 读取同一份最新业务数据，通过 API 执行的操作能在页面追踪；不同入口不各自计算不同的可用状态。
- 同站多来源只展示一个站点，独立账号余额不被合并；签到重复上报不增加记录。
- 网页失败但 API 成功能分别呈现；目录可见但任务失败不会进入已验证模型。
- 允许测活的渠道验证通过后自动恢复指定模型，New API 回读一致；低质量渠道按配置策略降级，限流和余额问题不误算质量。
- 当日额度跨过重置时间后正确退出优先池；限时任务复用原调度，不重复执行或投递。
- 真实调用被多个来源采集时不重复计算；无法关联的来源单列，不伪造完整统计。
- “禁止测活”对所有渠道入口生效。RP 渠道不出现在中心的查询、MCP、New API 与 Notion 中；Chrome 书签的酒馆目录保持移出时的内容，不因本次调整删除、移动或改名书签。
- 历史失败渠道完整可见，复查状态和下次时间明确；明确移除的渠道不会被恢复。
- 自动发现新模型能进入评估并接入；客户端当前选择与原任务的暂停状态保持不变。
